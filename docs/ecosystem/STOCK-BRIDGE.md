# Read-only shared-business stock bridge

Status: implemented for review behind disabled switches; not deployed or release-ready. Owner-approved audience (2 November 2026): the existing Crosstopher seller/business, with everyone who has Fitsin access sharing visibility. Crosstopher's UI, seller records, normal authentication, stock state machine, OCR/backlog and marketplace behavior remain unchanged.

## What the slice does

Crosstopher `GET /integrations/fitsin/stock-summary` uses a separate bearer credential and a server-configured seller ID. Fitsin `GET /v1/stock-summary` remains behind the existing shared app-code middleware and forwards only to that configured origin/route. No browser/app receives the bridge credential or a caller-controlled seller selector. A returned seller mismatch is rejected. The bridge credential does not participate in normal seller authentication and must never reuse a seller login token. The bridge rejects configuration whose key hash matches any seller login token. This does not revoke a reused login token or change normal seller authentication: provision a separate key.

The source response is an explicit allowlist: `schemaVersion: 1`, `sellerId`, `generatedAt`, and `counts` containing `drafts`, `active`, `reserved`, `pendingManual`, `doubleSales`, `failedListings`, `openQuestions`. Counts reuse the current seller summary semantics and SQL filters. Failed listings and questions count listing/review rows; they are not necessarily distinct garment counts. Pending manual removals can overlap conflicts. Active includes POS-only stock and does not mean online publication. No money, asking-price sales totals, photos, personal details or physical-stock coverage estimate crosses the bridge.

Fitsin returns an envelope with `status` (`disabled`, `fresh`, `unavailable`, `unauthorized`), `complete`, nullable `data`, and configured `sellerId` when available. Success also includes `schemaVersion: 1`, `lastSuccessAt`, `sourceObservedAt`, and a configured HTTPS root `url`. `sourceObservedAt` is when Crosstopher generated the summary, not the latest garment edit or a source revision. The existing summary uses sequential scoped reads; this is not a transactional cross-table snapshot. All seven counters must validate as nonnegative safe integers. Errors never manufacture zeros or expose upstream response bodies. A missing/wrong source scope clears saved client data through `unauthorized`; invalid counters/schema/timestamps within the correct scope return `unavailable`, retaining any same-scope saved data with its original timestamp.

The optional Today card refreshes independently of sales/week, shows urgent counters first, labels active stock accurately, and links to Crosstopher's existing root. It does not add new routes/filters to Crosstopher. The link opens its normal authentication flow; the bridge does not grant browser login. A same-scope outage retains the in-memory last success with an explicit saved-data notice and original last-fetched time. Consumer disablement, source authorization failure or scope change discards it. Source 404/503 (including a disabled/misconfigured Worker) is an outage, so an existing same-scope card remains explicitly saved; this is not an immediate revocation mechanism. There is no new disk cache. A cold failure displays an error, not fabricated counts.

## Configuration for a later approved activation

No actual secrets or live bindings were configured in this task. Keep these switches disabled until the final local batch and review. This is a configuration reference, not deployment authorization.

| Component | Settings |
| --- | --- |
| Crosstopher Worker | `FITSIN_BRIDGE_ENABLED=true`, `FITSIN_BRIDGE_SELLER_ID=<existing seller ID>`, `FITSIN_BRIDGE_TOKEN=<separate random secret of at least 32 non-whitespace characters>` |
| Fitsin backend | `CROSSTOPHER_BRIDGE_ENABLED=true`, `CROSSTOPHER_BASE_URL=https://<Crosstopher origin>` (origin only, no credentials/query/path), `CROSSTOPHER_SELLER_ID=<same existing ID>`, `CROSSTOPHER_BRIDGE_TOKEN=<same separate secret>` |
| Fitsin iOS build | `STOCK_SUMMARY_ENABLED=YES`; project default is `NO`. Missing/unexpanded setting also disables the client request/card. |

All three switches default off; no existing deployment setting or secret was changed. Restart the backend after configuration changes; captured scope/credential state cannot change under an in-flight read. Worker disabled/misconfigured/unauthorized responses are respectively 404/503/401 and never return counts. Consumer disablement returns a successful `disabled` envelope so the optional card can hide cleanly.

The checked-in Worker asset routing includes `/integrations/fitsin/*`, so the route reaches its handler instead of the SPA fallback, including while disabled. This routing declaration does not enable the bridge.

Only HTTPS source origins are accepted in application wiring. The service unit tests explicitly allow loopback HTTP fixtures; that option is not wired into the application server. Redirects are rejected, response bodies are capped at 16 KiB, and the entire read/body is bounded to five seconds without retries. Concurrent reads share one flight; later refreshes always recheck the source. Responses carry `Cache-Control: no-store`. No source credential, successful response or failed authorization is persisted.

Live Cloudflare Access/routing policies and the actual origin/seller ID remain unverified. Confirm server-to-server access to this exact read-only route during separately approved activation; do not disable existing app authentication or expose /api write routes to make it work. Secret rotation requires updating both services; pending reads can finish under the prior configuration. Existing in-flight data and five-second request bounds are not instant revocation guarantees.
